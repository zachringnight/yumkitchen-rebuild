## Four traps that cost real time here

Read these before touching anything. Each one has already produced work that
looked correct and was not.

### 1. Verify your viewport before trusting any measurement

The in-app Browser pane reported a `0x0` viewport during this work. At zero
width, `getBoundingClientRect` returns garbage, `scrollHeight` inflates
wildly (one page measured 29,424px; the real number at 1440x900 was 10,958),
and `srcset` selection picks the smallest variant, which then looks like an
image-resolution bug that does not exist.

Run `() => innerWidth + 'x' + innerHeight` first, every time. If it returns
`0x0`, switch to Playwright. Every number in this document was measured in
Playwright at 1440x900.

### 2. A green metric is not a fixed problem

The hero's text column ran shorter than its photo grid. A previous round
"fixed" it by stretching the column and pinning the proof row with `mt-auto`,
and reported **"measured gap: 0px."** True, and the wrong number: it relocated
the leftover height into a **308px void** in the middle of the column. The
metric was green and the page looked emptier.

Fixed in `13edb09` by centering a naturally-sized column. When you close a gap,
measure where the space went, not just where it left.

### 3. Some files you would edit are generated

- `social/.../data/review-manifest.json` is regenerated by `npm run render`.
  Hand-editing it survives exactly until the next render. The fix belongs in
  `scripts/render-all.mjs`. This bit once already.
- `campaign-copy.md` is likewise generated from the specs. The committed copy
  had drifted from its source and the render reverted two lines. If wording
  needs to change, change the spec.

### 4. `exports/` is gitignored

The 107 rendered masters live on disk only. They are current as of `e931621`.
A fresh clone has none of them, and `validate-motion` will fail until you run
`npm run render`. That is expected, not a regression.

## Patticake website: current state

Verified at 1440x900 and 390x844 on August 6. `verify.sh` PASSED, typecheck
and lint clean, axe 0 serious / 0 critical, Lighthouse mobile 100/100/100/100,
no horizontal overflow on mobile.

**The hero tells the gift in order:** how it arrives (the blue box), what is
inside (the cut cake showing three layers), how it is shared (slices on
plates). No two frames repeat a subject. This was the central fix of this
whole effort: it was previously a gifting business whose front page never
showed the gift.

**Zero same-page photo repeats** across the Patticake surfaces, and product
photos match their products (the coconut cake card carries a real coconut cake;
Baker's Man carries Baker's Man).

**`sizes` values run larger than each frame's visual width on purpose.** These
frames are taller than their source aspect ratios, so `object-cover` scales to
satisfy *height*, and a width-accurate `sizes` picks a variant that is too
short. The comment in `components/PatticakeHome.tsx` explains this. Do not
"optimize" those values down without re-checking at DPR 2.

Related subtlety: at DPR 1 the browser correctly requests 1x variants, so
asserting `naturalHeight >= rect.height * 2` at DPR 1 fails for reasons that
are not bugs. Check that the **srcset offers** a large enough candidate
instead.

### Where to improve it next

Ranked by what a viewer would notice.

1. **The hero's middle frame is still the weakest.** `10_layers_slice.jpg` is a
   landscape macro (1138x758) in a short wide slot. The uneven grid rows
   (0.62fr/1.38fr) were introduced specifically so `object-cover` scales it to
   width and shows most of the photograph, which helped. It is still the least
   appetizing of the three. A cleaner whole-cake-with-a-slice-out photograph at
   1400px+ would be a straight upgrade. `yum-patticake-layers.jpg` is exactly
   the right shot and is only 420x360, too small to use.
2. **Four Patticake photos on disk are unreferenced:** `01_cover.jpg`,
   `06_8inch_a.jpg`, `07_8inch_b.jpg`, `layers_slice_vertical.jpg`. The last is
   the old blurred hero lead, deliberately retired. The 8-inch pair are wedding
   or "Just Married" shots, deliberately kept off generic Patticake pages. Check
   any candidate visually before use.
3. **Photo sourcing is unblocked.** Zach removed the rights gating on August 5:
   any source may be used. The only remaining rule is **accuracy** (the photo
   must show the yum! item it claims to show). Sources already mined: the
   original-site archive at `/Users/zsoskin/codex outputs/yum-audit/03_assets/`,
   and an Apify pull of the owned @yumkitchen Instagram.

## Marketing assets: current state

Active pack: `social/yum-patticake-creative-launch-2026-07-14/`. Everything
else under `social/` is historical and quarantined by validator checks that
fail closed. Read `social/START-HERE.md` before touching any of it.

`node scripts/validate-motion.mjs` → **107/107 files, 41 checks, zero failures.**

Four content guards were added on August 6 after a review found craft problems
the existing 37 checks could not see:

| Guard | Catches |
|---|---|
| `carouselSetsNeverRepeatAPhoto` | a photo repeating inside one carousel, which reads as a broken upload mid-swipe |
| `everyBeatRendersBeforeThePanel` | copy written, approved, and never displayed because the text faded before that beat started |
| `messageCardsShowACakeCarryingAMessage` | "write the message" cards illustrated with a cake carrying no message |
| `reviewBoardCoversEveryStillCrop` | a founder approving the 4:5 still while five other crops ship unreviewed |

Deduplication is by **content hash, not filename**. The pack ships
byte-identical photographs under different names, so filename comparison
silently misses repeats.

### Where to improve it next

1. **No source-resolution guard exists.** The review asked for three guards
   (uniqueness, beat timing, source resolution); the first two shipped, the
   third did not. Nothing currently prevents a low-resolution source being
   scaled up into a 1080x1350 still. This is the most valuable single addition
   to `validate-motion.mjs`.
2. **A marketing-docs staleness review was started and never finished.** An
   agent was reviewing `PATTICAKE-LAUNCH-ROLLOUT.md`, `campaign-copy.md`,
   `social-copy-and-alt-text.md`, `carousel-publishing.md`,
   `platform-publishing.md`, and the toolkit master against the live site,

   `lib/patticake/catalog.ts`, and process copy contradicting
   `PatticakeProcessSteps.tsx`. **It was stopped before reporting. Its findings
   are unknown.** Treat this as unexamined ground, not as clean.
   One known delta is already recorded at the top of
   `PATTICAKE-LAUNCH-ROLLOUT.md`: the site's `#delivery-support` anchor
   collapsed, and the `how-to-patticake` carousel is note-first while the site
   is now checkout-first.

## Working agreements from this effort

- One PR per task, each naming what it closes.
- Confirm fixes in a real browser at a verified non-zero viewport, and paste
  the measured numbers into the PR.
- If a reported problem turns out to be a non-issue, close it with the evidence
  rather than inventing a change. This happened several times: two
  "unreferenced" images were byte-identical duplicates of referenced ones, and
  a marquee `aria-hidden` concern was already handled correctly.
- Never substitute a wrong photo to close a task. Flag the gap instead.
